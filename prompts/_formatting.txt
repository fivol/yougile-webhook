FORMATTING — read carefully. Applies to EVERY message you post into a
YouGile task chat from this system. All messages from this agent should
look like the same author wrote them — same density, same heading
discipline, same link style. Do not invent your own visual style.

CHANNEL RULES

- YouGile chat does NOT render markdown. It DOES render the `textHtml`
  field. For any reply longer than one short sentence, set BOTH `text`
  (plain prose fallback for notifications/search/copy) AND `textHtml`
  (what the user actually sees).
- NEVER put markdown into `text` (`**bold**`, backticks, `#` headings,
  `|` pipe-tables, `-`/`*` bullet markers). They render as literal
  characters in many YouGile clients.
- `text` should be plain prose: short paragraphs separated by single
  blank lines. No HTML in `text`.

DENSITY — this is a chat message, not a blog post

- NO <h1>. NO <h2>. They render enormous in the YouGile chat panel and
  look broken on mobile. This rule is non-negotiable.
- Use <h4> for the top heading of a multi-section message. Use <b>...</b>
  (inside a <p>) for a sub-section label inside a single block.
- If the message is under ~80 words, use NO headings at all — just
  paragraphs.
- One blank line maximum between sections. NEVER stack <br><br> or empty
  <p></p> to create vertical space.
- One <p> per paragraph. Do NOT wrap every line in its own <p> and do
  NOT use <p> inside <li>.
- Lists with one item are not lists — inline them in prose.
- Lists with multiple items: <ul><li>…</li><li>…</li></ul> with no
  blank lines or <br> between items, and no nested <p>.
- Aim for the whole message to fit one mobile screen. If you need more,
  consider whether half of it belongs in a follow-up reply or a PR
  description instead.

HTML TOOLKIT — use only these tags (drop any tag from future replies if
you observe it rendering as raw text in this deployment)

    structure : <p>, <br>, <hr>            (<br> sparingly)
    headings  : <h4>, <h3>                 (NEVER <h1>/<h2>)
    emphasis  : <b>/<strong>, <i>/<em>, <u>, <s>, <mark>
    lists     : <ul><li>, <ol><li>         (tight, no nested <p>/<br>)
    code      : <code> inline,
                <pre><code>…</code></pre> blocks
    quotes    : <blockquote>               (sparingly)
    links     : <a href="…">label</a>      (always wrap raw URLs)
    tables    : <table> only when a grid is genuinely needed

LINKS

- Every URL in `textHtml` must be wrapped in <a href="…">label</a> so it
  is clickable. The label should be human-readable (`#123`, `PR — fix
  X`, repo name) not the raw URL.
- For lists of PR links, use a compact <ul>:
      <ul>
        <li>app: <a href="…">#123 — short title</a></li>
        <li>infra: <a href="…">#456 — short title</a></li>
      </ul>

EXAMPLES — short reply (one sentence): plain `text` only is fine,
`textHtml` not needed.

EXAMPLES — structured reply: <h4> title, one <p> per paragraph, one
<ul> of bullets, no <br>, no <h1>/<h2>, no markdown.

DELIVERING A SKILL'S OUTPUT

- A skill you run inside a turn (`workspace`, `ship`, `/simplify`, a
  project skill) usually specifies its own chat output: which blocks, in
  which order, which status lines, where the test links go. That spec
  says WHAT to write; this file says HOW it reaches the user. Both hold —
  keep the skill's blocks and wording, render them with the HTML above.
- The mapping is mechanical: block title -> <h4> (or <b> for a sub-label
  inside a block), bullet list -> <ul><li>, `code`/paths/ids -> <code>,
  every URL -> <a href="…">label</a>, status lines -> their own <p>.
- Markdown in a skill's template (`**bold**`, `-` bullets, `##`, tables)
  is channel-agnostic shorthand for structure. CONVERT it. Never paste it
  into `text`, and never drop the structure to avoid the conversion.
- A skill's "chat output" step is not satisfied by printing the report in
  your own output — nothing you print reaches the user. It reaches them
  only as ONE `mcp__yougile-mcp__send_task_message` call.
- This matters most exactly where it is hardest to remember: the final
  report of a long implement/finish run, tens of thousands of tokens
  after these rules. A merge/finish report is a formatted message like
  any other.

=== ALWAYS ===

REPLY CONTRACT — this block is repeated at the end of every prompt,
because it is what breaks the reply when it is forgotten.

- Every message you send to the user goes through
  `mcp__yougile-mcp__send_task_message` (taskId = this chat's id).
- Longer than one sentence => set BOTH `text` (plain prose, no markdown)
  and `textHtml` (what the user actually sees). The tool's own schema
  calls `textHtml` "optional, rarely needed" — in this deployment it is
  mandatory, and a long reply without it is a broken reply however good
  its content is.
- `textHtml`: <p> per paragraph, <h4> for section titles (NEVER
  <h1>/<h2>), <ul><li> for lists, <a href="…"> around every URL, <code>
  for ids/paths/commands. No markdown characters anywhere.
- The final report of a skill run (implement, finish, merge — however
  long the turn was) is ONE such message, with the skill's blocks as
  headings.
